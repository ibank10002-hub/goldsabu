- 추가 방어: 승인 응답(`data`)의 키 prefix가 `live_`인지 `test_`인지 로깅하여 모드 혼동 차단.

## 2. 높은 위험 (실결제 전 반드시 해결)

### H-1. 승인 처리의 멱등성이 원자적이지 않음

`confirm-payment/route.ts:45-47`에서 `order.status === "paid"`면 조기 반환하지만, **SELECT(25행)와 UPDATE(74행) 사이가 원자적이지 않습니다.** 동시 요청 2건(예: 사용자의 새로고침 연타)이 들어오면 둘 다 SELECT에서 `pending`을 읽고 둘 다 토스 승인 API를 호출합니다. 토스가 중복 승인을 거절하므로 **이중 청구는 발생하지 않지만**, 두 번째 응답이 실패로 처리되어 `status`가 `failed`로 **덮어써집니다**(63-66행). 결과: **실제로는 결제 성공했는데 DB는 `failed`**.

**조치:** `pending → processing` 조건부 UPDATE(`.eq("status","pending")`)로 선점 락을 걸고, 반환 행이 0건이면 중복 요청으로 간주해 조기 반환.

### H-2. `create-order`에 인증·레이트리밋 없음

`create-order/route.ts`는 누구나 호출 가능합니다. 금액 위조는 막혀 있지만(아래 G-1 참조), **무한 `pending` 주문 생성**이 가능합니다. 무료 Supabase 플랜의 행 수/용량을 고갈시킬 수 있습니다.

**조치:** IP 기준 레이트리밋(예: 분당 5회) + `pending` 주문 TTL 정리 쿼리. 무자본으로 Vercel 미들웨어 또는 Supabase 쪽 cron으로 처리 가능.

### H-3. 환불/취소 처리 수단 0건 — FAQ의 약속과 불일치

- `schema.sql:11`에 `refunded` 상태값이 선언되어 있으나 이를 쓰는 코드 **0건**.

**조치:** 최소한 토스 결제취소 API를 호출하는 운영자용 라우트 1개 + `status='refunded'` 갱신. 자동화 UI는 2차로 미뤄도 되지만 **수동 수단은 오픈 전에 반드시 존재해야** 합니다.

### G-1. 금액 위조 차단이 서버에서 정확히 구현됨

## 5. 점검 환경의 한계 (투명하게 명시)

- **토스페이먼츠 승인 API 실호출은 검증하지 못했습니다.** 본 샌드박스의 egress 정책이 `api.tosspayments.com:443` 연결을 차단합니다(실측: HTTP 000, `connect_rejected`). 따라서 `confirm-payment`의 토스 연동부(49-72행)는 **정적 분석만** 수행했습니다. 코드상 인증 헤더 구성(`Basic` + `secretKey:` base64, 49-54행)은 토스 문서 규격과 일치합니다.
- **실제 Supabase 인스턴스에 대한 쿼리 검증도 불가**했습니다(C-2의 env 미설정). 따라서 `insert`/`update`의 런타임 동작은 미검증입니다. 단, 500 발생 지점이 Supabase 클라이언트 생성 이전이므로 **env만 채우면 그 이후 경로는 코드상 문제가 없을 것으로 판단**합니다(추정).
- 결제위젯 렌더링은 `/checkout` HTTP 200까지만 확인했습니다. 위젯 자체는 브라우저에서 토스 CDN을 로드하므로 **실 브라우저 검증이 별도로 필요**합니다.
